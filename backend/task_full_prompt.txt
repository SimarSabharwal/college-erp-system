# TASK: Redesign and Upgrade the Automated Timetable Generation Studio

You are a senior product designer, frontend engineer, and constraint-scheduling systems architect working on an existing College ERP application.

Your task is to redesign and improve the existing **Automated Timetable Generation Studio** into a polished, intelligent, configurable timetable-generation workflow.

Do not build a disconnected demo or replace the existing application architecture. Inspect the current codebase, database schema, API endpoints, scheduling algorithm, and existing timetable-generation UI first. Then implement the redesign using the existing technology stack and conventions.

The application already has teacher-subject assignments, room records, shift information, time slots, and scheduling constraints. Reuse this data.

The user should primarily configure the shift, rooms, scheduling requirements, and optimization preferences. They should not need to reassign teachers during every generation run.

---

# 1. DESIGN DIRECTION

Redesign the page to feel like a premium Apple-inspired academic administration product.

## Visual requirements

- Clean white or subtle off-white background.
- Dark, high-contrast typography.
- Restrained blue accents for primary actions.
- Green for validated or successful states.
- Amber for warnings.
- Red for errors or critical conflicts.
- Rounded cards with subtle borders.
- Minimal shadows.
- Generous but controlled spacing.
- Consistent iconography.
- Clear visual hierarchy.
- Smooth, subtle transitions.
- Professional, information-dense layouts without unnecessary clutter.

Do not use glassmorphism across the entire interface.

Avoid oversized headings, excessive gradients, decorative illustrations, giant cards, unnecessary empty space, and excessive use of colored backgrounds.

The interface should be compact enough that the main configuration and primary action are visible without excessive scrolling on a typical desktop screen.

Use responsive layouts for desktop, tablet, and mobile.

On mobile, stack the configuration sections vertically, make primary actions accessible, and convert the timetable grid into a usable scrollable or alternative compact layout.

## Preserve existing application styling

Inspect the existing design system before implementing the redesign.

Reuse existing components, fonts, spacing tokens, buttons, icons, modals, and form controls wherever appropriate.

Do not introduce a new component library or replace the application's entire design system without a clear technical reason.

# 2. RESTRUCTURE THE WORKFLOW

Replace the current five large workflow tiles with a more compact stepper or progress indicator.

Use these five stages:

1. Scope
2. Requirements
3. Constraints
4. Generate
5. Review & Publish

Show the active step, completed steps, and validation errors.

Allow users to navigate backward without losing configuration.

Do not require five separate full-page screens. Use a compact wizard, progressive disclosure, or a single page with clearly organized expandable sections.

The interface should remain understandable to a nontechnical college administrator.

Create a compact configuration section called "What should we schedule?"

- Semester.
- Program.
- Section or sections.
- Shift.

- Effective start and end dates.
- Existing timetable version, when applicable.

## Generation mode

Provide the following options:

### Generate New
Create a new timetable for the selected scope.

### Repair Existing
Preserve valid existing assignments and repair conflicts or missing sessions.

### Generate Alternatives
Generate multiple valid candidates with different optimization trade-offs.

### Regenerate Draft
Replace an existing unapproved draft only after confirmation.

Never silently overwrite a published timetable.

For each mode, explain the behavior in one short sentence.

# 5. STEP THREE: ADVANCED CONSTRAINT SYSTEM

This is the most important part of the redesign.

Replace the current small collection of constraint cards with a categorized constraint configuration panel.

Organize constraints into:

1. Faculty.
2. Students and Sections.
3. Rooms and Facilities.
4. Academic Rules.
5. Time and Breaks.
6. Optimization Preferences.

Each category should have a concise summary and an expandable details panel.

Use clear controls such as toggles, dropdowns, numeric inputs, and priority selectors.

Every constraint must have a clear description and indicate whether it is a hard constraint or a soft preference.

Do not create controls that look functional but have no effect on the backend.

## A. FACULTY CONSTRAINTS

### 1. Teacher-Subject Eligibility

Type: Hard constraint.

Default: Enabled.

Only use teachers assigned or otherwise authorized to teach the relevant subject.

Display the number of eligible teachers per subject.

### 2. Teacher-Subject-Shift Lock

Type: Hard constraint.

Default: Follow existing institutional configuration.

Reuse the existing teacher-subject-shift lock table and rules.

Display the locked assignments and their effects.

Do not silently override existing locks.

### 3. Teacher Availability

Type: Hard constraint.

Default: Enabled.

Respect:

- Teacher availability records.
- Approved leave.
- Blocked periods.
- Existing assignments.
- Other institutional restrictions.

### 4. Maximum Consecutive Classes

Type: Hard constraint.

Default: Use the existing institutional default, currently configured as two slots in the existing interface.

Allow authorized users to configure a permitted value.

Support teacher-specific exceptions if the existing data model supports them, or propose a schema migration if it does not.

Display a warning when an exception conflicts with institutional policy.

### 5. Maximum Daily Teaching Load

Type: Hard constraint.

Allow configuration in teaching periods or minutes.

Support institutional defaults and authorized teacher-specific limits.

### 6. Maximum Weekly Teaching Load

Type: Hard constraint.

Respect contractual or departmental workload limits where configured.

### 7. Workload Fairness

Type: Soft constraint.

Options:

- Disabled.
- Balanced.
- Strongly prioritized.

Reduce unnecessary differences in teaching workload between eligible teachers while respecting workload limits and existing assignments.

### 8. Teacher Idle Gaps

Type: Soft constraint.

Prefer fewer unnecessary gaps between a teacher's assigned classes.

Allow the administrator to adjust the priority.

### 9. Teacher Time Preferences

Type: Soft constraint.

Respect submitted preferences for preferred days and times.

Distinguish preferences from genuine unavailability.

A preference must never override a hard availability restriction.

---

## B. STUDENT AND SECTION CONSTRAINTS

### 1. No Section Double-Booking

Type: Hard constraint.

A section cannot attend two sessions simultaneously.

### 2. Required Sessions

Type: Hard completeness requirement.

Schedule every required teaching session.

If all sessions cannot be scheduled, explain which sessions remain unscheduled.

Never silently discard a required lecture.

### 3. Subject Distribution

Type: Soft constraint.

Avoid excessive repetition of the same subject on a single day.

Prefer spreading sessions throughout the week.

Allow configurable minimum gaps between sessions of the same subject.

### 4. Student Idle Gaps

Type: Soft constraint.

Minimize unnecessary gaps between classes.

### 5. Daily Academic Load

Type: Hard or soft according to institutional policy.

Support configurable minimum and maximum teaching periods per day.

### 6. Consecutive Student Classes

Type: Soft constraint by default.

Allow the institution to limit consecutive classes or prefer short breaks between demanding sessions.

Do not apply a hard restriction unless the institution explicitly configures one.

### 7. Shared Student Groups

Type: Hard constraint when enrollment data is available.

Prevent overlapping sessions for student groups that must attend both.

If the application does not yet have student-level enrollment data, clearly identify this as a future capability rather than pretending it is already enforced.

---

## C. ROOM AND FACILITY CONSTRAINTS

### 1. Room Double-Booking

Type: Hard constraint.

A room cannot host overlapping sessions.

### 2. Room Capacity

Type: Hard constraint.

The room must accommodate the relevant section's configured capacity.

If section enrollment or room capacity is missing, report the missing information.

Do not invent capacities.

### 3. Room Type Compatibility

Type: Hard constraint.

Laboratories must use compatible laboratory rooms.

### 4. Room Equipment

Type: Hard constraint when the requirement is mandatory.

Check required equipment against actual room records.

### 5. Room Availability

Type: Hard constraint.

Respect room availability for the complete session duration.

### 6. Room Stability

Type: Soft constraint.

Minimize unnecessary room changes for the same section.

### 7. Room Utilization

Type: Soft constraint.

Prefer efficient room usage without creating excessive student or teacher gaps.

### 8. Room Selection

Allow the administrator to:

- Include or exclude particular rooms.
- Select permitted room groups.
- Restrict generation to a specific floor or building.
- Define room preferences.
- Lock existing room assignments when appropriate.

Populate all options from actual room records.

Do not hardcode room names or assume every room is suitable for every subject.

- Confirm all hard constraints are satisfied.
- Confirm no blocking warnings remain.
- Show the difference from the currently published timetable.
- Ask for confirmation.

Allow authorized users to publish only validated, complete schedules unless the institution explicitly supports an approved exception workflow.

Store:

- Timetable version.
- Generation configuration.
- Candidate identifier.
- Generation timestamp.
- Validation results.
- Publishing user.
- Approval details, if applicable.
- Change history.

Support rollback to a previous published version.
